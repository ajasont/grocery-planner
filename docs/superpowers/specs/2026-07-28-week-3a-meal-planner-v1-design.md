# Week 3a: Meal Planner v1 Design

**Date:** 2026-07-28
**Parent spec:** `docs/superpowers/specs/2026-07-23-grocery-meal-planner-design.md` (§9 Recipe engine and meal planning)
**Milestone:** Week 3a — first slice of the Week 3 meal-planner milestone. Regenerate-single-meal, pantry integration, prefs UI, and lazy recipe-step generation are all deferred to 3b or later.

## Goal

Enable a Sunday planning session: user opens the app, taps "Plan my week", waits ~10 seconds, and sees a full 21-meal week (7 breakfast + 7 lunch + 7 dinner + 5–7 snacks) generated by Claude Sonnet 4.6 from this week's on-sale deals. View-only — no per-meal regenerate, no interactive editing. The plan for the week is persisted to Supabase and re-rendered on subsequent visits.

## Scope in / out

**In scope**
- New `/plan` page: empty state (generate CTA) and populated state (rendered plan).
- Server route that generates the plan (Anthropic Sonnet 4.6 → validator → persist).
- Full-week regenerate (destructive, replaces the current week's plan) with a confirm dialog.
- Layout: "today first + accordion peeks" (see below).
- Validator per parent spec §9: schema check → sanity check → variety check with one re-prompt.
- Header link from home to `/plan` (and an "empty plan" hint on home when no plan exists this week).
- Unit tests for validator, prompt builder, and generator (MSW-mocked Anthropic).

**Out of scope (deferred)**
- Regenerate a single meal (parent spec §9 "Regenerate a single meal") — 3b.
- Lazy recipe-step generation on meal tap (§9 "Recipe steps") — 3b.
- `/pantry` page (§11). Pantry table is read as empty for now.
- `/preferences` page (§19). `household_preferences` row is read with its empty seed defaults.
- Prior 3 weeks of meals — first plan has no history; on subsequent weeks the read layer picks up whatever's in `meals` automatically.
- Meal ratings UI (§9 "thumbs-up/down history").
- Streaming / progressive plan rendering. First cut is a full-page skeleton wait.

## User flow

1. **Home** (unchanged): deals list. Header gains a "Plan my week" link. When no plan exists for the current week, a subtle hint below the deals header reads `No plan for this week yet — plan it →`.
2. **`/plan` (empty)**: shows a "Generate this week's plan" CTA button. Below it, a one-sentence explanation of what will happen ("Uses this week's deals to suggest 21 meals — takes about 10 seconds").
3. **Generate**: POST to `/api/plan/generate`. Full-page skeleton (7 day-row shells with animated placeholder text) while Claude runs. On success, redirect to `/plan` which now renders the populated view.
4. **`/plan` (populated)**: today's day expanded and prominent at the top; other days rendered as one-line dinner peeks below, each expandable into full B/L/D via accordion. Snacks in a bottom section. "Regenerate" button in the header — tapping opens a confirm dialog ("This will replace your current plan"). Confirm → same generate flow as step 3.
5. **Errors**: full-page error card with the specific failure ("planner service unavailable" / "generated plan was invalid — try again"), plus a retry button that repeats the last generate.

## Layout

Chosen: option C from the brainstorm mockup (today-first + accordion). Snacks live in a "This week's snacks" section at the bottom. On a brand-new plan, only today is expanded by default; the user taps other days to expand them. Same behavior on return visits — no "expand-all on first view" special case for the first slice (revisit in 3b if it feels wrong in use).

Client-side interactivity: only the accordion open/close. Everything else is server-rendered.

## Architecture

**New module: `lib/meal-planner/`**

- `inputs.ts` — pulls the planner input from Supabase. Returns a `PlannerInput` struct:
  - `deals`: this week's on-sale deals joined to canonical ingredient info, cheapest-store info per canonical (reuses / extends `lib/deals/read.ts` grouping).
  - `pantry`: rows from `pantry` table (empty for MVP).
  - `preferences`: the singleton row from `household_preferences` (empty defaults).
  - `prior_meals`: names of meals from the last 3 `meal_plans` (empty for the first plan).
- `prompt.ts` — pure function `buildPrompt(input: PlannerInput): AnthropicMessages`. Follows §9 exactly (available ingredients, pantry contents, constraints list). Uses the prompt-cache pattern from `lib/normalization/mapper.ts`: the constraints text and output-schema block go in a cached system prefix; only the deal list + pantry + prior meals go in the user turn.
- `generate.ts` — orchestrates one round-trip: call Anthropic via the existing `lib/anthropic/client.ts` singleton, parse JSON, run validator, re-prompt once on variety violation. Returns `GeneratedPlan` or throws typed errors (`AnthropicError`, `JsonParseError`, `ValidationError`, `VarietyError`).
- `validator.ts` — pure function `validate(plan: unknown, deals: Deal[]): ValidationResult`. Three-step: schema (Zod-style), sanity (≥3 ingredients, cook time in [5,120] min, canonical IDs exist), variety (no cuisine >2x/week). Returns `{ ok: true, plan }` or `{ ok: false, kind: 'schema'|'sanity'|'variety', reason: string }`.
- `persist.ts` — `savePlan(plan: GeneratedPlan, weekOf: string): Promise<PlanId>`. Deletes any existing plan for the same `week_of` first (regenerate = replace), then inserts one `meal_plans` row, N `meals` rows, N×M `meal_ingredients` rows in a single Supabase transaction.
- `read.ts` — `getCurrentWeekPlan(): Promise<RenderablePlan | null>`. Reads `meal_plans` for the current week, joins to `meals` and `meal_ingredients`, returns a shape grouped by day and pre-sorted by meal-type (breakfast → lunch → dinner) with snacks separated.

**New routes**

- `app/plan/page.tsx` — server component. Calls `read.ts`. Renders empty state or populated view.
- `app/plan/DayAccordion.tsx` — client component. Wraps a single day's rows; owns open/closed state; toggles via a button on the day header. No global state.
- `app/api/plan/generate/route.ts` — POST handler. Runs `inputs → prompt → generate → validator → persist`, then returns 303 redirect to `/plan`. Called by the Generate + Regenerate buttons (both are forms that POST to this endpoint).

**Reuses**

- `lib/anthropic/client.ts` — existing singleton.
- `lib/db/client.ts` — existing Supabase server client.
- `lib/deals/read.ts` — extended (or `inputs.ts` calls it) to fetch the deal set with canonical info; no re-implementation.
- `getCurrentWeekOfISO()` helper — extract from `lib/deals/read.ts` into `lib/dates.ts` if it isn't already there, since `read.ts` and `inputs.ts` both need it.

## Data model

**No migrations.** All required tables (`meal_plans`, `meals`, `meal_ingredients`, `pantry`, `household_preferences`) exist from week 1 (`supabase/migrations/0001_initial_schema.sql`). Row inserts start populating them for the first time.

`meal_plans.status` — the schema has a `status text default 'draft'` column. For this slice, everything writes `'draft'` and the UI treats any plan for the current week as "the plan". A future slice can introduce an approve gate when it becomes useful.

## Error handling

| Failure | Behavior |
|---|---|
| Anthropic API 5xx / timeout | Surface "planner service unavailable — try again" with retry button. No auto-retry. |
| Malformed JSON from Anthropic | One silent retry (per parent spec §9). If second attempt also fails, error surface. |
| Sanity check fails (missing ingredients, bad cook time, unknown canonical) | Error surface with the specific reason. No auto-retry — structural, not transient. |
| Variety check fails (cuisine repeat) | One targeted re-prompt with a "reduce cuisine X" instruction. Accept even if borderline after that. |
| Persist DB error | Error surface, retry button. |

The full-page skeleton stays visible during retries; the user doesn't see failure until we give up.

## Testing

Pure-function tests only for the first cut:

- `tests/meal-planner/validator.test.ts` — valid plan passes; missing-ingredients fails with `kind: 'sanity'`; bad cook time fails; unknown canonical_id fails; cuisine >2x flags `kind: 'variety'`.
- `tests/meal-planner/prompt.test.ts` — built prompt includes deals, pantry, prefs, prior meals sections; constraints list matches spec §9.
- `tests/meal-planner/generate.test.ts` — MSW-mocked Anthropic. Happy path returns a `GeneratedPlan`. Malformed-JSON-then-retry path succeeds on second attempt. Persistent-malformed path throws `JsonParseError`.

No end-to-end route tests. Browser smoke-test against a local dev server (per project convention from weeks 1 and 2a) is the acceptance gate.

## Decisions locked in

- **Snack count**: exactly 7 (one per day). Parent spec §9 says "5–7"; we pick 7 for deterministic layout. Revisit in 3b if it feels excessive.
- **Cheapest-store per canonical for the prompt**: pick the row with the min `sale_price` across retailers for that canonical, include the retailer name in the deal entry. If the planner picks wrong-store meals in practice, refine later.
- **Route pattern**: API route (`app/api/plan/generate/route.ts`) rather than a server action — easier to curl for manual testing and matches the existing `app/api/admin/*` handlers.

## Success criteria

- On a Sunday, generating a plan takes ≤20 seconds end-to-end (Claude round-trip + validator + persist).
- Generated plans read as usable meals a real household would eat (subjective — Jason's judgment on first Sunday).
- Validator catches at least one malformed / low-quality response in the first 10 generations (proves it's doing work).
- Refreshing `/plan` after generation renders the persisted plan without re-calling Anthropic.
